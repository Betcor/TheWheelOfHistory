# 0044. Транспорт: LocalChannel і TCP, з'єднання на сервері й клієнті

- **Статус:** прийнято
- **Дата:** 2026-10-01

## Контекст

Протокол (ADR 0043) готовий, але клієнт досі викликав `EmbeddedServer.newWorld` напряму, а окремий сервер нічого не
слухав. Потрібен транспорт — Netty `LocalChannel` для вбудованого сервера й TCP для окремого — з одним шляхом коду для
всіх режимів. Відкрите питання з ADR 0043: чому зі спільним однопотоковим event loop сервера й клієнта `LocalChannel`
губив відповідь.

## Рішення

- **Обсяг:** транспорт, обробка з'єднання на сервері (рукостискання → створення світу → карта частинами), клієнт
  `kolo.client.net` і перехід екрана нового світу на повідомлення. `SessionActor` зі стан-машиною сесії, лобі, фази
  року й запис через `WorldStore` — наступними кроками.
- **Розмова без мережі** — `server/session/ClientSession`: повідомлення клієнта → `Reply(messages, close)`. Помилка
  гри стає `ServerMessage.Error`; з'єднання закривається, якщо помилка сталася до привітання (інше перше
  повідомлення, інша версія чи контент, невалідний контент сервера — `hello_expected`) або порушено порядок розмови
  (`ProtocolException`, зокрема `hello_repeated`). Помилка запиту після привітання (гравців поза межами) лишає
  з'єднання відкритим. Інший виняток — баг сервера: обробник його логує й закриває з'єднання без відповіді.
  Генерація світу — `NewWorlds.generate` (перенесено з `EmbeddedServer`), контент — `LazyContent` (при першому
  зверненні, невдача не запам'ятовується).
- **Сервер** — `server/transport/GameServer`: `bindLocal()` (нова `LocalAddress` на кожен виклик) і
  `bindTcp(address)` (порт 0 — будь-який вільний) з тими самими обробниками (`ProtocolPipeline.server` +
  `ConnectionHandler`). Свій event loop на кожен транспорт і **один потік сесій** `kolo-session`: генерація триває
  секунди, тож не в event loop; один потік зберігає порядок повідомлень і не потребує блокувань у сесії (заготовка
  для `SessionActor`). Пошкоджене повідомлення чи завеликий фрейм (`frame_too_large`, місце `frame`) — `Error` і
  закриття: межі фреймів у потоці вже ненадійні. Закриття — після запису останнього повідомлення, щоб клієнт отримав
  причину. Усі потоки — демони; `close()` закриває адреси й з'єднання.
- **Вбудований сервер** — `EmbeddedServer.startWithBundledContent()` → `address()` (`LocalAddress`), `contentHash()`
  (клієнт одиночної гри грає контентом сервера; завантажує контент — не з потоку UI), `close()`. Метод `newWorld`
  прибрано: клієнт говорить із ним лише повідомленнями.
- **Окремий сервер** — `DedicatedServerMain [--port N]`, типово `Protocol.DEFAULT_PORT` = 19700 (не частина формату
  повідомлень, версії не змінює). Контент завантажується одразу: невалідний — сервер не стартує (код 1); невірні
  аргументи — код 2. Зупинка — сигналом процесу (shutdown hook).
- **Клієнт** — `client/net`: `ServerConnection.connect(address, contentHash)` (Local чи TCP за типом адреси) →
  `CompletableFuture`, що завершується після `Welcome` і `Handshake.confirm`; `createWorld(...)` →
  `CompletableFuture<MapView>`, одночасно — один запит. `ConnectionHandler` працює лише в event loop свого каналу.
  Помилки: `ServerErrorException` (сервер відповів `Error` — гравець бачить `Texts.error(code, details)`),
  `GameException` (пошкоджене повідомлення, інша версія), `ConnectionClosedException` (розрив, немає сервера). Два
  винятки клієнта — не в `engine/error`: це не помилки гри, кинуті тут, а отримане повідомлення й стан з'єднання.
  `EmbeddedGame` (вбудований сервер + з'єднання, відновлюється, якщо закрилося) реалізує `WorldSource` — те, з чим
  працює `NewWorldScreen`. Новий текст `app.error.connection_lost`.
- **Спільний event loop — причина знайдена.** Зі спільним потоком `LocalChannel` доставляє повідомлення співрозмовнику
  синхронно всередині `flush` відправника. Клієнт отримав `Welcome` ще всередині власного `flush` для `Hello`, і його
  відповідь, записана з `channelRead`, натрапила на захист `AbstractChannel` від повторного входу в `flush` (`inFlush0`):
  лежала у вихідному буфері до наступного `flush`, а запис завершився лише при закритті (`ClosedChannelException`).
  Рішення: клієнт і сервер ніколи не ділять event loop (у клієнта — свій потік `kolo-client` на з'єднання), а сервер
  відповідає з потоку сесій, тож синхронного повторного входу немає.

## Наслідки

- Один шлях коду для одиночної гри й мережі: клієнт не знає, чи сервер у процесі, чи по мережі, крім вибору класу
  каналу за адресою.
- Поки один потік сесій на весь сервер: клієнти окремого сервера чекають генерації світів одне одного. З
  `SessionActor` — потік на сесію.
- Клієнт для віддаленого сервера ще мусить мати власний хеш контенту — зараз його дає лише `EmbeddedServer`
  (з'явиться з екраном мережевої гри).
- Тести: `ClientSessionTest`, `LazyContentTest`, `NewWorldsTest`, `ConnectionHandlerTest` (сервер, `EmbeddedChannel`
  зі справжніми фреймами), `GameServerTest` (Local і TCP, кілька клієнтів, розбіжність версій, зупинка, зайнятий
  порт), `EmbeddedServerTest`, `DedicatedServerMainTest`, смоки `EmbeddedServerSmokeTest` і `DedicatedServerSmokeTest`;
  у клієнті — `ConnectionHandlerTest` (юніт), `ServerConnectionTest` (з вбудованим сервером), оновлені
  `ClientSmokeTest` і фікстура `TestWorlds` (карти — через з'єднання, як у грі).
