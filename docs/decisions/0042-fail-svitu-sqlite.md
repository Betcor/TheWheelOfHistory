# 0042. Файл світу SQLite (`WorldStore`) і мігратор схеми

- **Статус:** прийнято
- **Дата:** 2026-10-01

## Контекст

Світ у будь-якому режимі — файл збереження, який переноситься між режимами (GD §21). Снапшоти карти й стану з хешами
вже є (ADR 0041); бракує самого файлу: де лежать снапшоти, як пишеться рік, як файл переживає зміну схеми між
версіями гри. Сесій, наказів, подій і гравців у коді ще немає.

## Рішення

- **Де.** `server/persistence`: `WorldStore` (публічний, `AutoCloseable`), записи `WorldMeta`, `SavedTurn`; пакетні
  `Migrator`, `Migration`, `SqlScript`, `Gzip`, `SaveErrors`. Драйвер — `sqlite-jdbc` (уже був у залежностях
  сервера), чистий JDBC.
- **Лише таблиці з даними.** Перша міграція `0001_world.sql` створює `world_meta` (один рядок: назва, seed, хеш
  контенту, хеш карти, момент створення), `world_map` (один рядок, gzip карти — пишеться раз), `turns` (рік, хеш
  стану, момент збереження) і `snapshots` (рік, gzip стану). Таблиці `players`, `session_state`, `orders`, `events`,
  `rolls`, `proposals`, `chat_messages` з'являться новими міграціями разом зі своїми даними — угадані наперед
  колонки однаково довелося б мігрувати. Відступи від ескізу §8.1: `turns.seed` (seed року виводиться з seed світу й
  року — додати разом з `resolveTurn`, якщо знадобиться), `world_meta.mode` і `settings_json` (з лобі),
  `world_meta.schema_version` (версія снапшота — у самому снапшоті, версія файлу — у `schema_migrations`).
- **Файл світу.** `PRAGMA application_id` = `0x4B4F4C4F` («KOLO»): чужа база SQLite, порожній файл і не-SQLite —
  `SAVE_MALFORMED` (`part` = `file`, `problem` = `not_a_world_file`). Журнал — WAL, зовнішні ключі ввімкнено; після
  закриття журнал прибирається, тож закритий світ — один файл.
- **Створення** (`WorldStore.create(file, name, map, initial)`) пише все в тимчасовий файл поруч
  (`.<ім'я>.creating`) і лише потім перейменовує: недописаного світу не буває. Наявний файл не перезаписується
  (`SAVE_FILE_ERROR`, `problem` = `file_exists`); залишок попередньої невдалої спроби прибирається. Після запису файл
  відкривається звичайним `open` — тобто прочитане перевіряється одразу.
- **Відкриття** (`open`): файлу немає — `SAVE_FILE_ERROR` (`file_missing`), SQLite не створює новий. Далі
  `application_id` → міграції → метадані → карта (розпаковується, читається суворо, хеш має збігтися з
  `world_meta.map_hash`) → останній рік.
- **Рік** (`saveTurn(StateSnapshot)`) — рядок `turns` і снапшот однією транзакцією; невдача лишає файл на попередньому
  році. Стан іншого світу (seed, хеш контенту, карта) або рік не пізніший за останній — `IllegalArgumentException`
  (помилка виклику, не даних). Снапшот зараз пишеться щороку; `turns` окремо від `snapshots`, тож проріджування (GD
  §6.4) додається без зміни схеми — `SavedTurn.hasSnapshot`.
- **Читання стану** (`loadState(turn)` → `Optional`, `loadLatest()`): розпакування (`bad_gzip`), SHA-256 JSON має
  збігтися з `turns.state_hash` (`state_hash_mismatch`), `StateSnapshot.read` (ADR 0041), рік снапшота — рік рядка
  (`turn_mismatch`), seed і хеш контенту — з метаданих (`world_mismatch`). Місце — `snapshots[<рік>]`.
- **Gzip** — стандартний `GZIPOutputStream`; байти стиснення не мусять бути однаковими між JVM, бо хеш рахується від
  канонічного JSON.
- **Мігратор — власний.** Скрипти `migrations/NNNN_назва.sql` у ресурсах сервера, перелік — у коді (ресурси в jar
  не перелічуються); версії 1, 2, … без пропусків, старі скрипти не змінюються. `schema_migrations(version, name,
  applied_at)`. Кожна міграція — окрема транзакція разом із записом версії; невдала відкочується, файл лишається на
  попередній версії. Перед міграцією вже існуючого файлу — копія `VACUUM INTO` поруч (`світ.koloworld.v1.bak`,
  наявні копії не перезаписуються: `…v1-1.bak`). Версія файлу новіша за відому грі — `SaveVersionException` з
  `part` = `file`, `version`, `supported`. Драйвер виконує за виклик лише перший оператор, тож `SqlScript` ділить
  скрипт: коментар `--` до кінця рядка, оператор закінчується `;` у кінці рядка (без тригерів і літералів з `;`).
- **Помилки.** `SAVE_FILE_ERROR` отримав подробиці: `file` (лише ім'я файлу), `operation` (`create`, `open`,
  `save_turn`, `load`, `close`), `problem` (`file_exists`, `file_missing`, `io_error`) або `sqlite_code`.
  `SAVE_MALFORMED` — також `part` = `file` з місцем-таблицею (`world_meta`, `turns`, `snapshots`) і проблемами
  `not_a_world_file`, `missing_row`, `no_turns`, `no_snapshots`, `bad_timestamp`.
- **Не потокобезпечний:** файлом володіє один актор сесії; двох записувачів одного файлу не передбачено й не
  блоковано.
- Час (`created_at`, `saved_at`, `applied_at`) — `Clock` (у тестах — сталий), текст ISO-8601 UTC; у хеш стану не
  входить.

## Наслідки

- Найбільший світ (16 гравців, багато NPC): створення файлу ~100 мс, рік ~25 мс (знімок + gzip + транзакція),
  відкриття з читанням останнього стану ~90 мс; файл ~0,4 МБ + ~115 КБ на рік — 200 років без проріджування
  ~23 МБ (бюджет 100 МБ).
- Кожна нова таблиця — нова міграція; тест мігратора перевіряє перехід зі старішої версії з резервною копією.
- Міграції снапшотів (JSON між `schemaVersion`) — окремо, з першою зміною `WorldState` (ADR 0041).
- Далі: `SessionActor` пише рік через `WorldStore`, протокол і `LocalChannel`; клієнтові — «Завантажити».
